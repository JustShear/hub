# Decision log

Chronological record of significant decisions. Full reasoning for each lives in its linked ADR (`docs/decisions/`) where one exists; this log is the short, dated index.

| Date | Decision | Detail |
| --- | --- | --- |
| 2026-07-26 | Standalone app, independent staff auth, no embedded Shopify admin app | SRS v1.1 change log, Section 1.3 |
| 2026-07-26 | Customer email via Klaviyo (profile + event tracking), not a transactional provider | SRS v1.1 change log, Section 1.3 |
| 2026-07-27 | Prisma pinned to 6.19.3 instead of latest 7.x | Avoids two disclosed vulnerabilities in 7.x's bundled dev-database tooling; no functional loss for this app's usage |
| 2026-07-27 | Prisma client `engineType = "binary"` | Dev machine is Windows ARM64; the default "library" engine is an x64 native addon that can't load into an arm64 Node process |
| 2026-07-27 | Single in-process job poller, not a distributed queue | [ADR-0001](decisions/0001-single-instance-job-execution.md) — **acceptable only for single-instance deployment** |
| 2026-07-27 | Deferred full automated `shop/redact` / complete `customers/redact` | [ADR-0002](decisions/0002-deferred-shopify-privacy-erasure.md) — **BLOCKING BEFORE PRODUCTION**, dedicated future milestone required |
| 2026-07-27 | Opaque JSON for addresses/discounts/fulfilments, not normalised | [ADR-0003](decisions/0003-opaque-commerce-json.md) — revisit when an operational feature needs to query into these |
| 2026-07-27 | Added proposed Milestone "Privacy, Retention and Shopify Data Erasure" | See `docs/architecture/architecture-review.html` milestone plan; must complete before production go-live |
| 2026-07-28 | Interim local-disk proof-file storage behind a provider-agnostic `StorageAdapter`, not Cloudflare R2 | [ADR-0004](decisions/0004-interim-local-disk-proof-storage.md) — **must be replaced before production go-live**, and compounds ADR-0001's single-instance constraint until then |
| 2026-07-28 | Reused `OrderProofSummary.PROOFS_NOT_STARTED` for both "undetermined" and "no proofs created yet"; added only `READY_TO_SEND`/`BLOCKED` as genuinely new enum values | Avoids a breaking rename across Milestones 06B/07 code for a distinction with no behavioural difference this milestone; see `docs/development.md` "Proof groups and proof versions (Milestone 08)" |
| 2026-07-28 | Mapped the milestone's 3-value proof-requirement vocabulary onto the schema's existing 4-value `ProofRequirementValue` enum, leaving `PARTIALLY_REQUIRED` reachable-but-unused | Avoids a schema rename; `PARTIALLY_REQUIRED` is reserved for a later milestone once a group can span lines with genuinely different requirement decisions |
| 2026-07-28 | Added a `ProofRequest`/`ProofRequestGroup` bundling model instead of using Milestone 08's reserved per-`ProofVersion` token fields | [ADR-0005](decisions/0005-proof-request-bundling.md) — a single customer link needs to open several proof groups at once, which a per-version token can't represent |
| 2026-07-28 | `sendProofRequest` returns the raw token to its direct caller, once, at creation time | The one deliberate exception to "never re-expose the raw token" — matches the milestone's own "display or email the raw token only at creation time" rule; the internal HTTP route does not forward it to the browser response |
| 2026-07-28 | Klaviyo dispatch failures fold into the existing `IntegrationFailure`/`IntegrationAttempt` mechanism (`integration: EMAIL`) rather than a bespoke email-delivery-state model | Reuses the already-built backoff/retry classification and staff-facing integration-issue surfaces instead of duplicating them |
| 2026-07-28 | `ProofReminder` has no stored "cancelled" status — eligibility (request completed/revoked/expired, order cancelled) is re-checked live by the poller every tick instead | Avoids a second place that could disagree with the request's own authoritative status; documented as technical debt (item 18) for the "why didn't this fire" staff-visibility gap it creates |
| 2026-07-28 | Replaced the placeholder `ProductionExport` model (required `proofVersionId`, couldn't represent the no-proof-required export path) with `ProductionArtwork`/`ProductionArtworkOrderLine`/`ExportBatch`/`ExportBatchItem` | [ADR-0006](decisions/0006-production-artwork-export-model.md) — zero rows, zero application references at removal time; new shape supports both eligibility paths, per-revision history, and audited batch export with re-export lineage |
| 2026-07-29 | `ExportBatch` creation runs as a two-phase reserve-then-finalise sequence (a `PREPARING` row committed before any file I/O, then a short CAS-checked transaction that flips state) rather than one long transaction wrapping the ZIP build | Keeps file I/O out of an open database transaction, and makes a failed export a permanent, visible `FAILED` audit row instead of a silently discarded batch number |
| 2026-07-29 | Embroidery (`.emb`) files are accepted by trusting the declared extension, the one exception to "verify every file by content" | No single reliable public signature exists across vendor embroidery-digitising formats; documented as technical debt (item 20) rather than rejecting legitimate files |
| 2026-07-30 | Added `ProductionJob`/`ProductionTask`/`ProductionQualityCheck`/`ProductionIssue`/`ProductionNote` and a second independent `ShopifyOrder.productionSummary` rollup | [ADR-0007](decisions/0007-production-queue-workstation-model.md) — production grouping reuses the existing 5-value `DecorationMethod` taxonomy rather than a new workstream enum; job/task idempotency comes from `@@unique([exportBatchId, decorationMethod])` and `@@unique([exportBatchItemId])` respectively, not a separate dedup mechanism |
| 2026-07-31 | Added `FreightShipment` with no packing gate — eligible once `productionSummary === "COMPLETE"`, permission-gated only | [ADR-0008](decisions/0008-starshipit-freight-integration.md) — reuses the `ExportBatch` reserve-then-finalise shape; carrier/service/packaging-preset are free text, no confirmed Starshipit discovery endpoint exists |
| 2026-07-31 | The Shopify tracking write-back (`fulfillmentCreate`) is the app's first-ever Shopify GraphQL mutation, and runs as a separate, independently-failable step after shipment creation, never inside the same success path | [ADR-0008](decisions/0008-starshipit-freight-integration.md) — failures fold into the existing `IntegrationFailure`/`IntegrationType.STARSHIPIT` mechanism (reserved since Milestone 02); `notifyCustomer: false` is deliberate and permanent, carrying forward the same exclusion since Milestone 09 |
| 2026-07-31 | Freight label cancellation is internal-only — never calls a Starshipit void/cancel API | [ADR-0008](decisions/0008-starshipit-freight-integration.md) — no such endpoint is confirmed in the public reference this milestone; documented as technical debt (item 29) |
| 2026-08-01 | Added `WarehousePickJob`/`WarehousePickItem`/`WarehousePickQuantityUpdate`/`WarehouseIssue`/`WarehouseNote` and a second independent `ShopifyOrder.warehousePickSummary` rollup — a checklist workflow, not real inventory tracking | [ADR-0009](decisions/0009-warehouse-picking.md) — this milestone was described as "Milestone 12" in the architecture review's original ordering, but shipped after Starshipit freight per an earlier explicit user choice, so it's Milestone 13 in the actual build/decision-log numbering |
| 2026-08-01 | Warehouse pick-job auto-creation lives inside `recalculateOrderProductionSummary` itself (same transaction as the summary flip) rather than as a follow-up call at each of its 6 existing call sites | [ADR-0009](decisions/0009-warehouse-picking.md) — pure DB writes with no external I/O, so atomicity with the summary flip is stronger, not weaker, than a separate follow-up step; idempotent via `WarehousePickJob`'s own `@@unique([orderId])` |
| 2026-08-01 | A short pick does not block handover to packing — it auto-creates a non-blocking `WarehouseIssue` (`STOCK_SHORTAGE`) instead | [ADR-0009](decisions/0009-warehouse-picking.md) — explicit user scoping decision; freight's own eligibility rule (Milestone 12) is deliberately left untouched, not retroactively gated on picking |
| 2026-08-02 | Added a unified `ExceptionCase`/`ExceptionCaseResolution` model for returns, warranty claims, and production defects, with refunds/credits record-only and no Shopify money movement | [ADR-0010](decisions/0010-exception-cases.md) — mirrors the ProductionIssue/WarehouseIssue precedent (one entity + a reason-category enum) rather than three separate tables; this milestone was called "Milestone 15" by the user, following the architecture review's much finer-grained original numbering, but is Milestone 14 in the actual build/decision-log numbering |
| 2026-08-02 | Removed the unused, zero-reference `Reprint`/`ReprintAsset` models (reserved since the original Stage One schema, predating `ExportBatch`/`ProductionJob`) | [ADR-0010](decisions/0010-exception-cases.md) — mirrors Milestone 10's removal of the similarly-stale `ProductionExport` placeholder; REPRINT/EXCHANGE resolutions reuse the real `createExportBatch`/`reExportBatch` pipeline instead |
| 2026-08-03 | Migrated proof/artwork/export/freight-label storage to Cloudflare R2 via a factory swap (`NODE_ENV`-selected), not a hard replacement | [ADR-0011](decisions/0011-cloudflare-r2-migration.md) — closes ADR-0004's "must be replaced before production go-live"; untested against a real bucket in this environment (mocked-client tests only), flagged as required verification on first real deploy |
| 2026-08-03 | Barcode scan-to-fill validates strictly for Warehouse (single SKU per pick item, override-on-mismatch) but is purely informational for Production (a task can span multiple SKUs, nothing reliable to validate against) | [ADR-0012](decisions/0012-barcode-scan-to-fill.md) — closes technical-debt item 34; both paths call the same pre-existing `recordPickQuantity`/`recordProductionQuantity` functions, scanning is a new input path, not new mutation logic |
| 2026-08-03 | Added a 20-second client-side polling-revalidation hook (`usePollingRevalidation`) to every queue/board route, paused while the tab is backgrounded | Deliberately client-side revalidation, not server-side real-time push (no WebSockets/SSE) or cross-instance job coordination — narrows staleness on the four queues/board (technical-debt items 9/12/26) without touching or weakening ADR-0001's single-instance constraint |
| 2026-08-03 | Extended the existing Production report-page pattern to Warehouse and Exceptions rather than building a shared generic reporting component | Each domain's report shape (jobs handed over vs. cases opened/resolved) differs enough that a shared abstraction would need parameterizing every metric anyway; three small, independently-readable report pages matched the codebase's existing precedent better than a premature abstraction |
| 2026-08-03 | Real notifications thread `unreadNotificationCount`/`notifications` through `app.tsx`'s loader → `AppShell` → `AppHeader`, exactly mirroring the pre-existing `integrationIssueCount` pattern | Notification creation added at three call sites (exception-case assignment, blocking warehouse issue, blocking production issue) — non-blocking issues stay silent, matching the existing signal-to-noise judgement already implicit in this codebase's issue-severity model; `notifications.actions.tsx` has no permission gate beyond being signed in, since every mutation is scoped to the caller's own `staffUserId` |
| 2026-08-03 | Generalized `SavedView` with a `scope` column, but built a separate, simpler generic domain layer (`app/domain/saved-views/generic-saved-view.server.ts`) for Production/Warehouse/Exceptions rather than reusing the board's typed `BoardFilters`/`SavedViewConfig` schema | The board's schema is genuinely board-specific (priority/dueDateStates/tags/etc.) and doesn't fit these queues' own filter shapes; the generic layer instead stores each queue's URL search params verbatim as an opaque string map — a deliberate, documented deviation from the original plan's assumption that the existing `SavedViewsMenu` component was "already generic" (it wasn't — confirmed by reading it directly) |
| 2026-08-03 | Manual security review found and fixed one real IDOR gap (`createFreightShipment`'s idempotency-key duplicate check had no `shopId` scoping) and added in-memory, per-process login rate limiting (5 failed attempts per email+IP per 15 minutes) | See `docs/security-review.md` for the full review — permission ordering, secrets handling, XSS, session cookie flags, and `npm audit` (0 vulnerabilities) all checked out clean without changes needed. The saved-views ownership check (`staffUserId`-scoped, not `shopId`-scoped) was reviewed and accepted as a pre-existing, safe design (predates this milestone), not changed |
| 2026-08-03 | Backup/restore is a supplementary manual mechanism (`pg_dump`/`pg_restore` custom-format scripts), not a replacement for Render's managed automatic daily backups | `docs/backup-and-restore.md` — drilled against the real local dev Postgres container (dump/restore round-trip verified identical in row/table counts) rather than just documented from the tools' own docs |
| 2026-08-03 | Corrected a stale README assumption that a second Render process would run the background job worker | The job poller has always started in-process from `app/root.tsx`'s loader (idempotent, since Milestone 04) — no second process exists or is needed; `docs/deployment.md` states the real one-Web-Service topology and restates the single-instance constraint where an operator will actually be looking |
| 2026-08-03 | Production readiness checklist verdict: **not yet approved for production** | `docs/production-readiness-checklist.md` — the one remaining blocker is the deferred Shopify privacy/data-erasure milestone ([ADR-0002](decisions/0002-deferred-shopify-privacy-erasure.md)), explicitly out of scope for this "final polish" milestone from the start; everything else synthesised from the technical-debt register is either resolved this milestone or an accepted, non-blocking limitation |

| 2026-08-03 | Redesigned the Kanban board to a 9-column, mostly tag-driven set (New → Order Sheet Printed → Waiting on Customer → Proof Being Prepared → Proof Sent → Changes Requested → Proof Approved → Exported for Print → Pack), and added a Pack column with inline freight controls | [ADR-0013](decisions/0013-kanban-lifecycle-tags-and-pack-column.md) — 2 tags read-only/externally-applied, 4 written by the Hub itself via a new `syncOrderLifecycleTag` function (using the already-reserved `IntegrationType.SHOPIFY_TAG_UPDATE` enum value — zero migrations needed); `FULFILLED` moved to its own special view; requires a one-time pre-cutover tag backfill (`scripts/backfill-lifecycle-tags.ts`) for orders already mid-flight |
