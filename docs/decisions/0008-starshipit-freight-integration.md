# ADR-0008: Starshipit freight labels and the first Shopify write (Milestone 12)

**Status:** Accepted.

## Context

Milestone 11 gets an order to `productionSummary === "COMPLETE"` but nothing yet gets a freight label or leaves the building. There is no Packing milestone yet — per the user's explicit scoping decision this milestone, none is added now. Every prior milestone (04–11) has only ever *read* from Shopify; this is the first milestone that needs to *write* back to it (the carrier tracking number).

## Decision

**No packing gate.** `evaluateFreightShipmentEligibility` (pure, `app/domain/freight/freight-eligibility.ts`) checks only `productionSummary === "COMPLETE"`, no existing active (`PREPARING`/`CREATED`) shipment for the order, and the order isn't cancelled. Staff are trusted to only trigger the freight action once the order is genuinely, physically packed — there is no separate `Packing`/`Fulfillment` model this milestone.

**One new model, reserve-then-finalise, reusing Milestone 10's own pattern.** `FreightShipment` (`FreightShipmentStatus`: `PREPARING`/`CREATED`/`FAILED`/`CANCELLED`) follows the exact three-phase shape `createExportBatch` established: (1) reserve a `PREPARING` row with a committed `idempotencyKey` before any I/O, (2) call the real Starshipit API — `createStarshipitOrder` then `printStarshipitLabel` — entirely outside any DB transaction, storing the returned label PDF via the existing `StorageAdapter`, (3) a CAS `updateMany` (`where: {id, status: "PREPARING"}`) finalisation update. `failFreightShipment` mirrors `failExportBatch` (writes `FAILED` + reuses the `cancelReason` field for the failure reason). No `@@unique([orderId])` — an order could in principle have more than one shipment (a split shipment); "at most one active shipment per order" is enforced at the application level via a count check inside eligibility, the same way `ExportBatch` enforces its own sequencing without a hard DB constraint for that particular rule.

**Carrier, service level, and packaging preset are free-text, not enums.** Starshipit's public API reference (`support.starshipit.com`) has no confirmed discovery endpoint for an account's actual configured carriers, service levels, or parcel presets — these are account-specific and already configured on Starshipit's own side, per the user's own confirmation ("we have multiple carriers and options — standard is default"; "we have default sizes of parcels in StarshipIT"). Staff enter `carrierCode`/`carrierServiceCode` (required, UI defaults the service field to "Standard") and an optional `packagingPresetName` — omitting the latter lets Starshipit apply its own account default. Starshipit's own API is the validator; an invalid combination comes back as a real rejected outcome, not a client-side guess. If Just Shear wants a fixed dropdown later, that's a small follow-up (one labels-module file), not a blocker.

**The Shopify tracking write-back is a separate, independently-failable step — never inside the same transaction or the same success path as shipment creation.** This mirrors Milestone 11's own "export success must never be undone by a downstream job-creation failure" precedent exactly: a Shopify sync failure must never undo a shipment that already genuinely happened with the carrier. `syncFreightTrackingToShopify` (`app/domain/freight/sync-tracking-to-shopify.server.ts`) is the app's first-ever Shopify GraphQL **mutation** — a two-step call: query `order(id).fulfillmentOrders.nodes{id, status}` for an `OPEN` fulfillment order, then `fulfillmentCreate(fulfillment: {trackingInfo: {number, company, url}, notifyCustomer: false, lineItemsByFulfillmentOrder: [{fulfillmentOrderId}]})`. On success: sets `FreightShipment.shopifyFulfillmentId` and advances `ShopifyOrder.workflowStatus` to `FULFILLED` (an enum value already reserved since the board-column work in Milestone 06B, never reachable until now) transactionally, and calls `recordIntegrationSuccessAfterFailure`. On any failure: records via the **pre-existing** `IntegrationFailure`/`IntegrationType.STARSHIPIT` mechanism (reserved in the schema since Milestone 02) with action `"freight_tracking_sync"` — meaning the existing `/integrations` queue and header badge (`IntegrationIssueIndicator`) pick up freight sync failures automatically, with zero new UI, since both already query by the shared `IntegrationType`/`OPEN_STATUSES` contract. A staff-triggered "retry Shopify sync" action re-invokes the same function for a `CREATED` shipment whose `shopifyFulfillmentId` is still null.

**`notifyCustomer: false` is deliberate and permanent for this milestone.** Customer shipping notifications are explicitly out of scope, carrying forward the same exclusion Milestones 09–11 already stated.

**Cancellation is internal-only.** `cancelFreightShipment` is a record-correction (`status → CANCELLED`, requires a reason) and never calls a Starshipit void/cancel API — no such endpoint is confirmed in the public reference this milestone. Voiding the actual label with the carrier remains a manual process outside the Hub (technical-debt item 29).

## Current limitations

- No carrier/service/package-preset discovery or validation UI — free-text entry, validated only by Starshipit's own API response.
- No label voiding/cancellation with the carrier — cancellation is an internal record only (technical-debt item 29).
- The exact `/api/orders/shipment` request body was inferred from Starshipit's published response fields and a third-party integration write-up, not a fully published request schema — flagged for confirmation against a real sandbox response the first time this is actually exercised with real credentials (technical-debt item 30).
- No multi-parcel/split-shipment support beyond what a single Starshipit order-plus-label call naturally returns.

## Risks

None beyond the already-tracked ADR-0001/ADR-0004 constraints (single-instance, local-disk storage) — freight labels reuse the same `localDiskStorageAdapter`. The first-ever Shopify write does introduce a new failure surface (Shopify could reject the mutation, e.g. no open fulfillment order, already fulfilled elsewhere) — handled entirely through the existing `IntegrationFailure` retry/visibility mechanism rather than a new one.

## Conditions that trigger reconsideration

- If Just Shear wants a fixed carrier/service/packaging-preset dropdown instead of free text — once a confirmed discovery endpoint exists or the account's fixed set is manually documented.
- If a genuine packing/warehouse milestone is added later — the current no-gate design (permission-gated only) would need revisiting once a real "packed" state exists to gate on instead.
- If Starshipit's void/cancel endpoint becomes confirmed and is worth wiring up, so cancelling in the Hub also voids the label with the carrier.

## Required future work

None blocking — this is a complete, stable shape for Milestone 12 and the deferred warehouse/packing/returns work that would build on it later.

## Addendum: verified against a real account, and a real-account surprise (post-Milestone 16)

Connected to a real Starshipit account for the first time and found something the original design didn't anticipate: **this account has its own native Shopify integration**, which auto-imports every order directly from Shopify — independently of, and before, this app ever touches it. Confirmed directly: a real order (#36355) already existed in Starshipit with a carrier and service level already assigned by Starshipit's own sync, well before any freight action was taken in the Hub.

This meant `createStarshipitOrder` — which assumed this app was the *only* thing ever creating orders in Starshipit — would have created a genuine duplicate order for every single order, not just a hypothetical edge case. Fixed by adding `findStarshipitOrderByOrderNumber` (`app/adapters/starshipit/starshipit-client.server.ts`) and changing `createFreightShipment` to look up the existing Starshipit order first (by the Shopify order number, stripped of its leading `#` — confirmed that's how Starshipit's native sync stores it) and only fall back to `createStarshipitOrder` if genuinely not found, e.g. a different Starshipit account without this native sync enabled.

**A second real-account surprise, worth calling out because it contradicts the "normal" REST assumption**: Starshipit's order-lookup endpoint returns **HTTP 200 with `{"success": false, "errors": [...]}` for an order number that doesn't exist — never a 404.** Confirmed directly against the real account with a deliberately-nonexistent order number. `findStarshipitOrderByOrderNumber` reads `success` from the response body, not the HTTP status, to detect "not found" — relying on a 404 here would have been wrong.

This closes the order-lookup portion of technical-debt item 30's "unconfirmed request/response shape" concern.

**Label creation itself has now been exercised for real, twice**, and technical-debt item 30 is fully resolved. Two real Australia Post labels were created against the real account during this verification (both cancelled afterward, never manifested) — confirming the request/response shapes in `printStarshipitLabel` are correct, and that `startCarrier`/`carrier_service_code` are genuinely account-specific and non-obvious: this account has **two separate Australia Post integrations** with distinct carrier codes — `AusPost` (display name "Australia Post," service codes like `3D85`, `PTI8`) and `MyPostBusiness` (display name "MyPost Business," service codes like `B30`, `BE1P05`) — sending a valid service code with the wrong one of these two carrier codes produces a clean Starshipit-side rejection (`"The product X you have entered is not supported"`), not a generic auth error. Staff configuring carrier/service codes for this account need to know which of the two Australia Post integrations a given service code belongs to.

**A real edge case in the find-or-create fix, worth documenting honestly**: once a Starshipit order already has a label printed against it, `findStarshipitOrderByOrderNumber`'s lookup did not reliably find it on a subsequent call — it came back "not found," and the fallback path correctly-per-its-own-logic created a *second* Starshipit order for the same Shopify order number. This is the mirror image of the duplicate-order problem the fix was built to solve, triggered from the opposite direction (an *already-shipped* order, not a same-day new one). In normal operation this narrow case is unlikely to matter: this app's own eligibility check (`evaluateFreightShipmentEligibility`) already blocks a second `createFreightShipment` call once the first one succeeds, since a `CREATED` `FreightShipment` row counts as an active shipment — the only way to hit this in practice is retrying against an order that was already printed at the Starshipit level without this app's own database knowing about it (exactly what happened during this verification, since one of the two real test labels was created via a direct API call outside the app, to diagnose an unrelated stale-credentials issue). Not fixed further this pass — documented here as a known, narrow limitation rather than silently left undiscovered.

**One practical lesson, not specific to Starshipit but rediscovered here**: a long-running local dev server process caches env vars at boot — adding real credentials to `.env` after the server is already running has no effect until it's restarted. Two of the 403 errors hit during this verification were caused by exactly that (the same root cause independently hit earlier with Klaviyo), not by anything wrong with the Starshipit integration itself. Worth remembering whenever a freshly-added credential appears to fail for no visible reason.

## Addendum: live rate comparison and editable package dimensions (post-Milestone 16)

Staff asked whether package weight/dimensions could be entered per-shipment and used to compare live carrier rates before committing to a label — this wasn't built in the original milestone, since Starshipit's `/api/rates` endpoint was assumed to be the rate-quoting mechanism and hadn't yet been exercised for real.

**`/api/rates` turned out to be unusable for this**: confirmed directly against the real account (and by Starshipit support, relayed by the user) that `/api/rates` only returns "checkout rates" — a separate configuration this account (and most accounts) doesn't have set up — and consistently returned `{"rates": [], "success": true}` despite six working carrier integrations. `/api/deliveryservices` (with `include_pricing: true`, which Starshipit defaults to `false`) is the correct endpoint: it returns every connected carrier's available service regardless of checkout configuration, with real pricing and an estimated delivery-date string per service.

**Added**: `getDeliveryServices` (`app/adapters/starshipit/starshipit-client.server.ts`) calls `/api/deliveryservices` and parses the real response shape (`services[]` with `carrier`, `carrier_name`, `service_code`, `service_name`, `total_price`, `pricing_breakdown["Predicted Delivery Dates "]`) into `DeliveryServiceOption[]`. `getDeliveryRates` (`app/domain/freight/get-delivery-rates.server.ts`) is a pure quote — it never touches `FreightShipment`, only builds the destination from the order's existing shipping address and returns options sorted cheapest-first. Weight/height/width/length were added to `FreightShipment` (all optional) so the same figures used for the quote are passed through to `printStarshipitLabel` when the label is actually created, ensuring the printed label matches what was priced. Weight is in kilograms; height/width/length are in metres — confirmed from Starshipit's own OpenAPI schema reference, not assumed.

**Scope decision**: this is a per-shipment feature on the existing Freight tab (order drawer), gated by the existing `freight_shipments.create` permission (an input method for an already-gated action, not a new capability — same pattern as barcode scan-to-fill from Milestone 16). A separate question was raised about surfacing this at the Kanban card level once an order enters a "Pack" stage — that would require a real packing/pack-stage model that doesn't exist yet (this milestone's own "no packing gate" decision, above, is still in effect) and was deliberately **not** built here; it remains unscoped future work if Just Shear wants it.
