Architecture Review — Pre-Build

Just Shear Production Hub

A read of the SRS (v1.0), the gaps worth closing before code, and the schema, architecture and milestone plan to build against.

Source Just_Shear_Production_Hub_SRS.docx, v1.0 Status Awaiting approval — no code written Prepared 26 Jul 2026

1. Project understanding

Just Shear needs one operational system spanning Shopify order intake through artwork proofing, production, picking, packing, freight, fulfilment, reprints and returns. Stage One — the only stage being built now — covers proofing and the handover into print. Everything after that (production queues, warehouse picking, Starshipit freight, returns) is deferred, but the data model has to anticipate them so Stage One doesn't get rebuilt later.

The single most important architectural decision in the document, and the one everything else hangs off, is this:

Central decision

Order status and proof status are separate, and an order can hold multiple proof groups, each with multiple retained proof versions. Approving or rejecting one proof group never touches the others. A hoodie with an embroidered logo and a printed back can have one proof group approved and exported while the other is still on its third revision — the order itself just reflects a summary of that mix.

Shopify stays the system of record for commerce — orders, customers, products, payments, fulfilment. The Production Hub is the system of record for everything operational: proof groups and versions, approvals, assignments, due dates, priority, notes, and — critically — the audit trail of every override and every integration failure. That boundary (Section 11.1 of the SRS) is clean and worth protecting; the biggest risk to the project is letting Shopify tags become a second source of truth instead of a visibility layer.

Six roles are defined (Administrator, Manager, Artwork/Proofing Staff, Print Staff, Packing Staff, Customer), with granular server-side permission checks and a strong emphasis on reasoned manual overrides — nothing bypasses the workflow without a recorded reason, and some overrides need a second approval. Reliability is treated as a first-class feature, not an afterthought: every external failure (Shopify, email, OPTIS parsing) lands in a visible, retryable queue rather than disappearing into a log file.

Overall this is an unusually well-specified SRS — it already names its own open risks (Appendix/Section 26), defines exact status enums (Appendix A), and gives Claude Code explicit working rules. The gaps below are the ones it doesn't resolve.

2. Issues, gaps & recommendations

Resolved — changes Section 21.1's implied stack

No individual Shopify staff logins. Confirmed: the Hub is a standalone application, not an embedded Shopify admin app. Staff never touch Shopify at all — they log in directly to the Hub with an email + password account an administrator creates for them. Shopify is reduced to a single backend integration: one custom app Admin API access token (generated once in Shopify admin → Settings → Apps → Develop apps), used server-side for order sync, tag updates and webhooks. No OAuth flow, no App Bridge, no per-shop multi-tenant installation flow, no Polaris — this is materially simpler than the embedded pattern Section 21.1 gestures at.

This also means the whole app — internal screens and customer proof pages alike — uses one visual system: the Just Shear tokens in Section 19.1. There's no split between "Shopify admin chrome" and "branded customer page" to maintain.

This is a significant change against Section 21.1 and Section 6's implied auth model. Per the SRS's own change-control rule (1.1), record this in the document's change log before Milestone 01: date, "standalone app + independent staff auth + single Shopify Admin API token, replacing embedded-app assumption," affected sections 6, 21.1, 21.2. Say the word and I'll draft that change-log entry into the SRS file itself.

Resolved

Customer email runs through Klaviyo, not a transactional provider. This changes more than the adapter name. Klaviyo doesn't expose a "send this exact email now, get a message ID back" API the way Postmark/SendGrid do — the Hub's job is to (1) upsert the customer's Klaviyo profile, then (2) track a custom event (e.g. Proof Ready For Review) with properties matching the Appendix B merge fields (order number, review link, customer first name). A Klaviyo Flow already built in the Klaviyo UI — not something the Hub can create via API — listens for that event and sends the actual email.

Practical effect on Section 12.2's delivery record: "sent" now means the event was accepted by Klaviyo, not that the email was delivered. The Hub can no longer independently guarantee end-to-end delivery — that responsibility splits across the API call succeeding (still tracked in the failure queue if it doesn't) and the Klaviyo Flow being live and correctly configured (Just Shear's side, in Klaviyo). Dependency to flag now: four customer-facing Klaviyo Flows need to exist before Milestone 17 can be tested end-to-end — proof sent, proof revision sent, printing-stage update, proof reminder (Appendix B's three templates plus the revision variant).

Staff-facing "emails" in Section 12.1 (proof approved notification, changes requested notification, integration failure alert) are not going through Klaviyo — per your answer, those stay in-app only via the existing Notification model, keeping staff profiles out of Klaviyo's customer lists and analytics entirely.

Resolved

Object storage: Cloudflare R2. Matches the recommendation — no egress fee on proof-image-heavy traffic, S3-compatible so the storage adapter interface doesn't care which provider sits behind it.

Hosting: Render. Managed Node hosting plus managed Postgres in one dashboard, with a native background worker process — the simplest fit for a single-store internal tool where nobody is signing up to run their own infrastructure. Cloudflare R2 is used purely for storage regardless of where the app runs; no coupling between the two decisions.

Gap · resolve before Milestone 15

Partial-export tag policy is named as an open risk (Section 26) but the build can't proceed without a default. When some but not all required proof groups on an order are approved/exported, does proof_approved / exported_for_print fire at the order level at all?

Recommendation: default to all required proof groups must reach the state before the order-level Shopify tag fires, expose partial_export_policy as an AppSetting so Just Shear can flip it to "any" later without a migration. The Kanban already has a "partially approved / partially exported" state for internal visibility, so nothing is hidden — this only governs what Shopify sees.

Improvement

Bulk historical import isn't addressed. Section 8.1 describes webhook-driven import for new/updated orders, but doesn't say how existing open orders are backfilled on first install. Iterating the REST/GraphQL API order-by-order at go-live risks rate-limit throttling on a store with any real order backlog.

Recommendation: add a one-time backfill using Shopify's Bulk Operations API on install, scoped to orders still open/unfulfilled, feeding the same idempotent import path used by webhooks.

Improvement

No numeric limits on uploads. Section 20 requires MIME/extension/size validation but sets no ceiling. Customer-uploaded artwork (print-ready files, embroidery digitising files) can be large.

Recommendation: set an explicit cap (suggest 25 MB per file for Stage One, configurable via AppSetting) and an explicit allow-list (png, jpg, pdf, svg, ai, eps; block all executables and archives by default).

Improvement

Real-time board updates aren't specified. Multiple staff will watch the same Kanban board simultaneously; the SRS requires "optimistic UI with rollback" (21.3) but doesn't say how one staff member's action becomes visible to another.

Recommendation: Stage One can ship with polling (10–20s) on the board view; note SSE/WebSocket push as a Stage Two/Five candidate rather than building it now.

Improvement

No accessibility target level named. Section 20 says "accessible controls and keyboard navigation" without a standard to test against.

Recommendation: adopt WCAG 2.1 AA as the acceptance bar for both the internal UI and the customer proof page (the latter is public-facing and unauthenticated, so it matters more, not less).

Already flagged in the SRS — noted, not re-litigated

Section 26 already lists OPTIS storage format, approval legal wording, customer-account proof access, file retention period, business-day/holiday rules and Starshipit rules as open validation items. These are correctly deferred to real data/legal review rather than guessed at — I haven't second-guessed them, only made sure the schema (Section 4 below) doesn't block whichever answer Just Shear lands on.

Decisions locked in

  • Object storage: Cloudflare R2, S3-compatible API, behind a provider-agnostic storage adapter interface.
  • Hosting: Render — web process, background worker and managed Postgres together.
  • Staff auth: email + password, admin-created accounts, no self-signup, no Shopify staff accounts involved anywhere.
  • Customer email: Klaviyo — profile upsert + custom event tracking, actual sending owned by Flows built in the Klaviyo UI.
  • Staff-facing alerts: in-app Notification only, no email leg at all.
  • Background jobs: Postgres-native queue (Graphile Worker) rather than adding Redis — one less moving part, and Render can run it as a second process against the same database with no extra infra.
  • Framework: React Router v7 as a standalone full-stack app (no Shopify app template, no App Bridge, no Polaris) — one Just-Shear-branded UI (Section 19.1 tokens) for both staff screens and the public proof pages.

4. Database schema

Prisma schema, organised by the domain groupings in SRS Section 22. Every model in the SRS's data-model table is represented; enums are pulled directly from Appendix A and the reason/category lists scattered through Sections 8–17 so nothing is invented that the SRS didn't already specify.

4.1 Shop, staff & access control

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

generator client {
  provider = "prisma-client-js"
}

model Shop {
  id             String   @id @default(cuid())
  shopifyDomain  String   @unique
  shopifyShopGid String   @unique
  adminApiToken  String   // static custom-app Admin API token (encrypted at rest, never logged) — no OAuth flow, single shop
  scopes         String
  timezone       String   @default("Australia/Adelaide")
  locale         String   @default("en-AU")
  currency       String   @default("AUD")
  installedAt    DateTime @default(now())
  uninstalledAt  DateTime?

  staffUsers          StaffUser[]
  roles               Role[]
  orders              ShopifyOrder[]
  settings            AppSetting[]
  decorationTemplates DecorationTemplate[]
  barcodes            Barcode[]
}

model StaffUser {
  id           String   @id @default(cuid())
  shopId       String
  shop         Shop     @relation(fields: [shopId], references: [id])
  email        String
  name         String
  passwordHash String     // bcrypt/argon2 — no Shopify staff account involved
  isActive     Boolean  @default(true)
  lastLoginAt  DateTime?
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt

  roles         StaffRole[]
  savedViews    SavedView[]
  notifications Notification[]
  assignments   OrderAssignment[]

  @@unique([shopId, email])
}

model Role {
  id            String   @id @default(cuid())
  shopId        String
  shop          Shop     @relation(fields: [shopId], references: [id])
  name          String   // ADMINISTRATOR | MANAGER | ARTWORK_STAFF | PRINT_STAFF | PACKING_STAFF
  isSystemRole  Boolean  @default(true)

  permissions RolePermission[]
  staff       StaffRole[]

  @@unique([shopId, name])
}

model Permission {
  id          String @id @default(cuid())
  key         String @unique   // e.g. "proof.send", "override.export_without_approval"
  description String

  roles RolePermission[]
}

model RolePermission {
  roleId       String
  permissionId String
  role         Role       @relation(fields: [roleId], references: [id])
  permission   Permission @relation(fields: [permissionId], references: [id])

  @@id([roleId, permissionId])
}

model StaffRole {
  staffUserId String
  roleId      String
  staffUser   StaffUser @relation(fields: [staffUserId], references: [id])
  role        Role      @relation(fields: [roleId], references: [id])

  @@id([staffUserId, roleId])
}

5.1 Components

Component Responsibility Notes
Staff web app Internal UI: board, drawer, settings, reports React Router v7, standalone (not embedded), email+password session auth
Public proof pages Customer-facing proof review & response Same server, separate route tree, same design system (Section 19.1 tokens), rate-limited
Application API Business rules, permission checks, orchestration Server routes/actions — every mutation goes through the RBAC layer first
Domain layer Proof-group/version state machine, override reason enforcement, reminder eligibility, proof-summary recalculation Framework-agnostic, unit tested in isolation
PostgreSQL + Prisma Operational records, workflow, audit Managed Postgres on Render; migrations committed to source control per 21.3
Object storage Proofs, artwork, uploads, production files Cloudflare R2 behind a storage adapter interface; signed upload/download URLs only
Job queue Klaviyo dispatch, Shopify sync, reminder sweeps, retries Graphile Worker (Postgres-native) as a second Render process — no Redis
Shopify adapter Admin API (GraphQL), webhook verification, tag sync Single static custom-app token, not OAuth; idempotent; internal state persists even when this adapter fails
Klaviyo adapter Profile upsert + custom event tracking for customer-facing sends Does not compose or send email itself — Klaviyo Flows (built in Klaviyo UI) own that; staff alerts never go through this adapter
Integration monitor Failure capture, backoff, escalation, resolution Feeds the header's unresolved-issues indicator (Section 14)

5.2 Cross-cutting rules that shape the code, not just the schema

  • Every mutation is server-side permission-checked — no client-side-only role gating. The RBAC layer (Role/Permission/StaffRole) sits in front of every domain action, not just route-level middleware.
  • Every external call is wrapped so failure never blocks the internal write. The order/proof-group/version state change commits first; the Shopify tag sync, email send, etc. are queued jobs that write to IntegrationFailure on exhaustion rather than rolling back the internal change.
  • Idempotency keys are mandatory on webhook processing, customer proof responses, outbound sync jobs and email jobs (Section 23.3) — enforced at the schema level via @unique constraints, not just application logic.
  • Nothing is overwritten. Proof versions are append-only and superseded, not edited in place; approvals, customer uploads and production exports are immutable once written.

6. Milestone plan

The SRS's own 23-milestone plan (Section 27) is sound and I haven't renumbered it — reordering here would just create drift between this document and the source of truth. Grouped into four phases with the exit criteria that actually gate moving on:

Phase 1 Foundation — Milestones 01–06

Repo, database, staff auth (email+password) & roles, single Shopify Admin API connection, order import, raw-data inspector, application shell. Exit criteria: a real Shopify order lands in Postgres via webhook, its OPTIS-style line properties are visible in the raw inspector, and a staff member can log in with their own Hub account and see the empty shell with correct role-based nav. Nothing about proofing is built yet — this phase is entirely about making Milestone 07 onward safe to build on real data instead of guesses.

Phase 2 Core proofing loop — Milestones 07–16

Kanban board, order-line assets, proof groups, proof versions, secure file storage, customer proof page, approval/changes, Klaviyo integration, tag sync, exported-for-print. Exit criteria: a staff member can take a real order from "New" through proof creation, customer approval (or revision loop), to exported-for-print, with Shopify tags reflecting each step, Klaviyo events firing correctly, and every version retained. This phase is the product — everything before it is plumbing, everything after it is safety net. Blocked on: the four customer-facing Klaviyo Flows (Section 2) need to exist in Klaviyo before this phase's proof-sent/reminder/printing-update milestones can be tested end-to-end — worth starting those in parallel with Milestone 07–10, not waiting until Milestone 14.

Phase 3 Reliability & operational control — Milestones 17–21

Reminders, overrides & audit, integration issue queue, no-proof-required handling, reprint/barcode data foundations. Exit criteria: nothing can be bypassed without a logged reason, nothing fails silently, and the reprint/barcode tables exist (unused) so Stage Two doesn't need a migration.
